# CDIF XAS Glossary — provenance and generation

Where the CDIF XAS vocabularies come from, how they were built, and what
is generated versus curated. Part of the `cdif/xasDocument/1.0` release
package.

Verified against the repository on 2026-08-25.

---

## 1. What the glossary is

`XAS_Glossary_SKOS.json` — **106 SKOS concepts** describing X-ray
absorption spectroscopy: measurement quantities, instrument components,
sample properties and processing results.

| | |
|---|---|
| Scheme URI | `https://w3id.org/cdif/xas/CDIF4XAS_Reference_Concepts` |
| Concept URIs | `https://w3id.org/cdif/xas/{localname}` |
| Conforms to | `https://w3id.org/cdif/conceptscheme/1.1` |
| Master file | `XAS_Glossary_SKOS.json` (repository root) |
| Release copy | `release/XAS_Glossary_SKOS_v2.json` (byte-identical) |

It is the **hub** of a concept-keyed architecture. XDI tokens and NeXus
paths are two *bindings* that both resolve onto it:

```
XDI token   --\
               >--  CDIF XAS concept  -->  CDIF JSON-LD
NeXus path  --/
```

That shape is the reason the vocabulary exists at all. Without a hub, an
XDI-derived document and a NeXus-derived one describing the same
measurement have no common term to agree on.

### Why these URIs were minted

The concepts are **not republished from an upstream vocabulary**. They
were assembled by reconciling three sources (§2) into one technique
vocabulary. URIs are minted under `w3id.org/cdif/xas/` because neither
source offers usable ones:

- **XDI defines no IRIs at all** — it is a header-token format.
- **The NeXusOntology PURLs under `purl.org/nexusformat` do not
  resolve**, and an open pull request renames every IRI.

A `w3id` namespace can be redirected to an official vocabulary later
without breaking data already published. This is a deliberate
mint-now-redirect-later position, not an assertion of ownership.

## 2. Sources

### The 89 original concepts

Assembled by reconciling:

1. **The XDI dictionary** — `XraySpectroscopy/XAS-Data-Interchange`,
   `specification/dictionary.md`. The bulk of the transmission-era
   vocabulary.
2. **NeXus NXxas application definitions** — both upstream and the XAS
   community fork.
3. **The project's XAS mapping spreadsheets** — now retired to
   `archive/` (§5).

**Definitions are sourced, not invented.** Every concept carries
`dcterms:references` citing the specification, dictionary or paper it
came from. Across the glossary those references resolve to:

| Host | Citations |
|---|--:|
| `doi.org` | 97 |
| `github.com` | 44 |
| `en.wikipedia.org` | 10 |
| `docs.xrayabsorption.org` | 7 |
| `dictionary.iucr.org` | 4 |
| others (`w3id.org`, `esrf.fr`, `iucr.org`, `csrri.iit.edu`) | 6 |

90 of 105 concepts carry at least one reference; 68 carry a
`skos:note`, 27 a `skos:notation` (the XDI token), and 11 a
`qudt:hasUnit`.

### Later additions

The gap analysis counted 89 concepts; there are now 105. The documented
additions are:

- **14 detection-mode concepts** added by
  `tools/add_detection_mode_concepts.py`. The glossary was written
  against transmission-mode XAS and had no vocabulary for electron
  yield, partial fluorescence yield or HERFD. Definitions are grounded
  in the NXDL `<doc>` text of the corresponding fields rather than
  written from scratch.
- **`sampledescription`** (`168c036`) for `NXsample/description`.
- **Five stubs** (`962315c`) for concepts that had previously existed
  only on the NeXus side.

Those overlap — the stubs predate the analysis's count — so the
arithmetic does not close cleanly from the commit log alone. Treat 105
as the authoritative figure and the list above as the record of what was
added and why, not as a reconciliation.

## 3. The three enumeration vocabularies

Separate concept schemes, not part of the glossary. They total ~478
concepts against a 105-concept glossary; folding them in would bury the
technique vocabulary under value lists.

| File | Concepts | Source class |
|---|--:|---|
| `XAS_edges_SKOS.json` | 39 | `NXabsorption_edge` |
| `XAS_emissionlines_SKOS.json` | 432 | `NXemission_line` |
| `XAS_detectionmodes_SKOS.json` | 7 | six `NXxas_*` app definitions + upstream `NXxas` mode enum |

All generated by `tools/import_nexus_enumerations.py` from:

```
https://github.com/XraySpectroscopy/nexus_definitions @ main
    contributed_definitions/
```

**This is the XAS community fork, not upstream NeXus.** The distinction
matters and is easy to lose:

- The 432 emission lines are the fork's complete IUPAC-notation
  transition list (`K-L1`, `K-L2`, `K-M1`, …) — every initial/final
  shell pair, not a curated subset. The count is correct, not a
  generation error; it matches the NXDL item-for-item.
- Every class these are built from is **fork-only**. Upstream NeXus has
  no `NXabsorption_edge`, no `NXemission_line`, and none of the six
  `NXxas_*` modes.

That second point caused a real defect. Until 2026-08-25 each concept
carried an `rdfs:seeAlso` pointing at `manual.nexusformat.org` — which
documents *upstream* NeXus. All 477 of those links (39 + 432 + 6) were
well formed and permanently 404. They have been removed; the source is
now cited in the scheme's `skos:note` as a GitHub blob URL on the
fork's own NXDL, which is both resolvable and the honest statement of
where the enumeration was read from.

Each enumeration concept carries `skos:broader` onto the glossary
concept it enumerates values for, without exception (39/39, 432/432,
7/7):

| Enumeration | `skos:broader` target |
|---|---|
| edges | `cdifxas:edgeanalyzed` |
| emission lines | `cdifxas:emissionline` |
| detection modes | `cdifxas:xasmeasurementmode` |

So the value lists *are* hierarchically attached to the glossary. The
flatness noted in §8 is within the glossary's own 104 top concepts, not
between the glossary and its value lists.

## 4. The SSSOM crosswalks

`crosswalk/` holds the mappings between the CDIF XAS hub and its two
bindings, expressed in **SSSOM** (Simple Standard for Sharing
Ontological Mappings).

| File | Rows | Direction | `object_source` |
|---|--:|---|---|
| `xdi-to-cdifxas.sssom.tsv` | 31 | XDI token → CDIF XAS concept | `w3id.org/cdif/xas/` |
| `xdi-to-cdif.sssom.tsv` | 4 | XDI header → schema.org property | `schema.org` |
| `cdifxas-to-nexus.sssom.tsv` | 52 | CDIF concept → NeXus path | `w3id.org/cdif/nxdl/` |
| `cdifxas-units.tsv` | 12 | CDIF concept → QUDT unit | — |

**Three sets, not two, and the split is by `object_source`.** Some XDI
headers carry bibliographic and rights metadata that CDIF models with
schema.org — `Publication.DOI` → `schema:identifier`,
`Publication.authors` → `schema:author`, `Publication.affiliation` →
`schema:affiliation` (closeMatch: XDI has one free-text string for the
whole author list, schema:affiliation attaches to a Person), and
`Spectrum.license` → `schema:license`. Putting these in the XAS set
would have made its declared `object_source` false, and minting an XAS
concept for "the DOI of the paper" would duplicate `schema:identifier`
for no gain.

### Why SSSOM rather than inline `skos:exactMatch`

The gap analysis recommended adding `skos:exactMatch` / `closeMatch` to
the concepts themselves. It was implemented as standalone mapping sets
instead, which is why the glossary contains no `exactMatch` at all.
The reasons are worth recording, because a reader looking for the
crosswalk inside the glossary will not find it:

- **Mappings and vocabulary have different lifecycles.** The NeXus fork
  is unstable — contributed status, competing branches. Mappings onto it
  will churn; the concepts should not.
- **SSSOM carries the metadata that makes a mapping reviewable**:
  justification, confidence, and an attributable author. An inline
  `skos:exactMatch` is a bare assertion with no provenance.
- **Two bindings, one hub.** Inlining would put XDI and NeXus mappings
  in the same node with no clean way to version or license them apart.

Each row carries `mapping_justification`
(`semapv:ManualMappingCuration`), `confidence`, `author_id` (ORCID) and
a free-text `comment`.

### Predicates in use

| | `cdifxas-to-nexus` | `xdi-to-cdifxas` |
|---|--:|--:|
| `skos:exactMatch` | 45 | 19 |
| `skos:narrowMatch` | 6 | — |
| `skos:closeMatch` | — | 1 |
| `skos:relatedMatch` | 1 | 2 |

The single `relatedMatch` in the NeXus set is deliberate and was called
for by name in the gap analysis: `cdifxas:calculated` ↔
`NXxas/ENTRY:NXentry/is_experimental` is **not** an `exactMatch`,
because the boolean polarity is inverted. Recording it as `related`
preserves the correspondence without asserting a false equivalence.

### Scope, and what the asymmetry means

The NeXus set covers **all six detection modes**. The XDI set covers
transmission only — *not* an omission: XDI is a transmission- and
fluorescence-era format and defines no tokens for retarding voltage,
emission-line selection or crystal-analyzer geometry. Those concepts
reach CDIF through the NeXus binding alone.

37 of 105 concepts have a NeXus mapping. The remainder are mostly the
17 EXAFS analysis products (χ(k), R-space transforms, filtered and
normalized variants), which the gap analysis deliberately left out of
scope — the XAS community has not touched processed data, and
`NXxasproc` in the fork is byte-identical to a 2008 upstream file.

### Object IRIs are provisional

`nxdl:` object IRIs are minted under CDIF `w3id` on the same
mint-now-redirect-later basis as the concepts, for the same reason: the
NeXusOntology PURLs do not resolve and an open PR renames every IRI.
Mappings target NeXus **base classes** wherever the concept is a
property of a kind of thing rather than a requirement of the technique.

### Validation

```bash
python crosswalk/build_crosswalk.py --check
```

**Mappings are curated; validation is automated.** The mapping table is
hand-written in the script; `--check` re-reads the glossary and the
NeXus definitions and fails if any subject or object no longer resolves.
Run it after changing a concept. `--no-rml-check` skips the
cross-check against `cdif-xas`'s RML mapping when no such checkout is
present.

## 6. Generated artifacts

Nothing below is hand-edited; all are derived from the master glossary.

| Artifact | Generator | Count |
|---|---|--:|
| `build/docs/concepts/{localname}.jsonld` | `tools/generate_concept_files.py` | 106 |
| `build/docs/index.html` | `tools/generate_glossary_html.py` | 1 |
| the three enumerations | `tools/import_nexus_enumerations.py` | 478 |
| the three SSSOM sets | `crosswalk/build_crosswalk.py` | 87 |

Per-concept files are self-contained, so
`https://w3id.org/cdif/xas/{localname}` can dereference to a single
concept.

**`build/` is gitignored and is not part of the repository.** It is the
GitHub Pages build root: `.github/workflows/build-docs.yml` runs both
generators, copies the four SKOS vocabularies and the LICENSE alongside
them, and publishes `build/docs` to `gh-pages`. That published site is
what `https://w3id.org/cdif/xas/{localname}` dereferences to. Do not
expect to find those 107 files in a clone — regenerate them.

This output used to be written to `/XAS-CDIF-1.0_release/`, which
collided with `archive/XAS-CDIF-1.0_release/`, the tracked copy of the
published 1.0 deliverable. Generated output for the *current* glossary
sat in a directory named for the *1.0 release*, and the two were
repeatedly mistaken for each other. Renamed to `build/` on 2026-08-25;
the archived 1.0 copy is unaffected.

The committed artifacts are the master glossary, the three enumerations,
the crosswalks, and everything under `release/`.

### Regeneration recipe

```bash
# after editing XAS_Glossary_SKOS.json
python crosswalk/build_crosswalk.py --check     # fails if a mapping subject broke
python tools/generate_concept_files.py          # per-concept JSON-LD
python tools/generate_glossary_html.py          # browsable HTML

# only when the NeXus fork changes
python tools/import_nexus_enumerations.py
```

## 7. Status of the gap-analysis recommendations

`XAS_Glossary_vs_NeXus_analysis.md` §8 made five recommendations.

| # | Recommendation | Status |
|---|---|---|
| 1 | Import the three enumerations | **Done** — as `skos:ConceptScheme`, not `skos:Collection` |
| 2 | Hand-write ~10 PFY/HERFD/PEY concepts | **Done** — all 10, plus 4 more |
| 3 | Add `exactMatch`/`closeMatch` | **Done** — as SSSOM (§4), not inline |
| 4 | Move unhomed concepts to an `xdi:` namespace | **Withdrawn** — premise was false, see below |
| 5 | Adopt the subclass hierarchy as `skos:broader` | **Not done** — see §8 |

Two deviations are deliberate:

**Rec 1 — schemes, not collections.** The three value lists are
independently citable vocabularies with their own identity and
lifecycle, not groupings within the glossary. A `skos:Collection` would
have made them internal to a scheme they are not part of.

**Rec 3 — SSSOM, not inline.** See §4.

**Rec 4 was withdrawn on 2026-08-25, because its premise was false.**

It proposed moving nine "genuinely unhomed" concepts to an `xdi:`
namespace, on the grounds that they are XDI-derived. Checked against the
XDI dictionary — which defines exactly 29 tokens — **eight of the nine
appear nowhere in it.** Only `fluxmeasuremethod` has an XDI origin,
generalising the four `Detector.i0/it/if/ir` descriptions.

Their real source is the **project's own mapping spreadsheets**, now in
`archive/` — the third source named in the scheme description (§2).
`XDI-CDIF-Mapping.xlsx` carries a `source` column separating `xdi` (61
rows, from the dictionary) from `dat` (14 rows, observed as extension
headers in real XDI data files, which the format permits and the
dictionary does not enumerate):

| concept | recorded origin |
|---|---|
| `fluxmeasuremethod` | `xdi` — generalises `detector.i0/if/ir/it` |
| `monochromatorangle` | `xdi` — `angle` |
| `scanmode` | `dat` — `Beamline.scan_mode` |
| `website` | `dat` — `Beamline.website` |
| `xasmeasurementmode` | upstream NeXus `NXxas/ENTRY/DATA/mode` |
| `installedoptions`, `calibrationmethod` | project-defined; no NeXus URI recorded |
| `monitormode`, `monitorpreset` | source column blank |

"XDI-derived" was half right in a way a dictionary check cannot see:
`scanmode` and `website` come from XDI **data**, not from the XDI
specification.

The `dcterms:references` to
[doi:10.5281/zenodo.14920226](https://doi.org/10.5281/zenodo.14920226)
that all nine carry is a **related reference, not a definition**. The
landscape report is a narrative survey; it defines none of the nine
(verified against the PDF text — eight score zero hits, and it does not
discuss token-level terms at all).

**This is the weakest link in the provenance chain.** The definitive
origin now lives only in retired spreadsheets that no tool reads and
that the glossary itself describes as superseded. If a concept's origin
is ever disputed, `archive/XDI-CDIF-Mapping.xlsx` and
`archive/XAS_Glossary_deprecated.xlsx` are the record — worth knowing
before they are cleaned up.

Moving them would also be a breaking change. Six —
`installedoptions`, `scanmode`, `calibrationmethod`, `website`,
`monochromatorangle` and `experimentdocumentation` — are `enum` members
constraining `schema:propertyID` in the xasDocument profile schema:

```json
"enum": [ "xas:edgeenergy", "xas:calibrationmethod",
          "xas:experimentdocumentation", "xas:installedoptions" ]
```

Renaming them changes the schema, the SHACL bundle, all seven release
examples and the RML mapping's `propertyIRI` construction, and
invalidates any document already emitting the old CURIEs.

What remains true from §3 of the analysis is the part about crosswalks:
these concepts have no NeXus counterpart, which is why they are absent
from `cdifxas-to-nexus.sssom.tsv`. They are equally absent from
`xdi-to-cdifxas.sssom.tsv` — necessarily, since a mapping needs an XDI
token to map from and there is none. The concepts the XAS profile leans
on most for operational metadata are precisely the ones neither source
vocabulary defines.

## 8. Future work

### Concept hierarchy (Rec 5)

The glossary is **flat**: 104 top concepts, no `skos:broader`, and a
single `skos:narrower` on `absorptioncoefficient`. The gap analysis
proposed adopting the NXxas subclass hierarchy —
`absorptioncoefficient` generalising the transmission / TFY / PFY /
TEY / PEY / HERFD variants.

**This requires domain expertise and is deferred.** Two obstacles are
worth recording so whoever picks it up does not rediscover them:

1. **The hierarchies classify different things.** NXxas subclasses
   classify *techniques* (application definitions); the glossary
   classifies *quantities*. There is no mechanical projection from one
   to the other — each pairing is a judgement.
2. **Half the nodes do not exist.** Of the six modes, only TFY
   (`fluorescenceabsorptioncoefficient`) and TEY
   (`electronyieldabsorptioncoefficient`) have a counterpart concept.
   Transmission has only a *normalized* variant, and PFY, PEY and HERFD
   have none at all. Building the tree as described means authoring
   three new concepts first.

A defensible starting shape, for whoever takes it on:

```
absorptioncoefficient
├── fluorescenceabsorptioncoefficient      (TFY)
├── electronyieldabsorptioncoefficient     (TEY)
├── referenceabsorptioncoefficient
└── [transmission variant — needs authoring]
```

with the four `normalized*` concepts as a **separate branch**:
normalization is a processing step, not a detection mode, and mixing
them in would make `skos:broader` mean two different things in one
tree.

Note also that `skos:hasTopConcept` and being the object of
`skos:narrower` are mutually exclusive — a concept narrower than
something is not a top concept. `electronyieldabsorptioncoefficient` is
correctly *not* a top concept today; what should change is that
`absorptioncoefficient`'s `skos:narrower` inlines the whole definition
instead of referencing it by `@id`. Any hierarchy work should use
`@id` references throughout.

### Pin the NeXus fork reference

The enumerations cite `XraySpectroscopy/nexus_definitions@main`. For a
release artifact that should be a commit SHA — the fork is unstable by
its own description, with competing branches, and `main` will move
under a published vocabulary. It was `89971f39` (2026-07-03) when the
enumerations were last regenerated. Pinning changes what "regenerate"
means, so it is a decision rather than a fix.

### `Scan.number` — deferred

`Scan.number` is the one XDI extension header in the mapping spreadsheet
left unmapped. It is a scan ordinal, presumably appended to a base
identifier to make a unique id within a dataset holding a set of scans.
Every XDI file in the example corpus holds a single spectrum, so the case
never arises here and nothing would exercise the mapping.

Worth noting rather than forgetting: XDI's dictionary already defines
`Column.N` for exactly this "N-th thing in a set" pattern, so if
scan-set datasets appear, `Scan.number` is the natural discriminator for
`schema:identifier` on each part.

### Contribution flowing the other way

CDIF's 17 EXAFS analysis concepts and its operational beamline concepts
(`calibrationmethod`, `fluxmeasuremethod`, `scanmode`,
`installedoptions`) fill real holes in the fork, whose `NXxasproc` has
been untouched since 2008. Worth taking to the XAS NeXus community as a
concrete proposal **while their definitions are still in flux**.
